# How practical-first resources choose a core

Research for [#40](https://github.com/jq-ln/curriculum-skills/issues/40), under the map [#38](https://github.com/jq-ln/curriculum-skills/issues/38). Sources checked 2026-11-22. Pro Git is quoted from its AsciiDoc source, [progit/progit2](https://github.com/progit/progit2) at commit `a013e32`, which is what [git-scm.com/book](https://git-scm.com/book/en/v2) renders.

## Answer

Every resource surveyed draws its core by a stated capability, then keeps it small by frequency: Pro Git's core is "how to use Git in the 80% of cases you'll encounter most often", MDN's is what you need to "design and build a basic, accessible web app ... and manage and deploy" it, Godot's is the four concepts "you will manipulate all the time". Each also admits a thin slice of model into the core when commands are hard to use without it, and leaves the rest of the model to a depth unit that the reader may take early or late.

None of them retracts a core claim in a later unit. They avoid it with four moves: an explicit forward pointer at the cut ("For now this magic invocation is all you need"), hedged wording ("usually strings"), procedures taught without a mechanism rather than with a wrong one, and depth units that add layers beneath the core model rather than replacing it. The one near-miss found is Pro Git's "Git doesn't think of or store its data this way" (deltas) in Chapter 1, which Chapter 10's packfiles, stored as deltas, qualify without saying so. It came from stating a core claim at the storage level instead of the model level.

For the outline agent, the strongest stated criterion combines a capability target from the Brief, frequency to choose among procedures, and a load-bearing test for theory, checked by closure under Prereqs. See [Candidate criteria](#candidate-criteria-for-the-core-cut).

## Per resource

### Pro Git

**Core.** Chapters 1 to 3 ("Getting Started", "Git Basics", "Git Branching") of ten ([table of contents](https://git-scm.com/book/en/v2)). Chapter 2 is the core proper; the Introduction says it covers "basic Git usage -- how to use Git in the 80% of cases you'll encounter most often", and that after it "you should be able to clone a repository, see what has happened in the history of the project, modify files, and contribute changes" (`book/introduction.asc`). The chapter opens "If you can read only one chapter to get going with Git, this is it. This chapter covers every basic command you need to do the vast majority of the things you'll eventually spend your time doing with Git" (`ch02-git-basics-chapter.asc`). Its summary restates the cut as a capability list: "creating or cloning a repository, making changes, staging and committing those changes, and viewing the history" ([2.8 Summary](https://git-scm.com/book/en/v2/Git-Basics-Summary)). Chapter 7 opens by confirming the boundary: "By now, you've learned most of the day-to-day commands and workflows that you need" ([7.1](https://git-scm.com/book/en/v2/Git-Tools-Revision-Selection)).

**Evident criterion.** Frequency ("80% of cases") bounded by a capability list. Model is admitted where it is load-bearing: section 1.3 teaches snapshots, SHA-1 checksums and the three states before any command, saying "here is the main thing to remember about Git if you want the rest of your learning process to go smoothly" ([1.3 What is Git?](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F)), and Chapter 3 teaches blobs, trees and commits because "To really understand the way Git does branching, we need to take a step back and examine how Git stores its data" ([3.1](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell)).

**Return to depth.** Two layers. Chapter 7 deepens commands the core used shallowly; Chapter 2 teaches `git reset HEAD <file>` as a procedure and stops: "For now this magic invocation is all you need to know about the `git reset` command. We'll go into much more detail about what `reset` does ... in [Reset Demystified]" (`book/02-git-basics/sections/undoing.asc`). Chapter 10, Internals, is last but optional in position: "we've made this discussion the last chapter in the book so you could read it early or later in your learning process. We leave it up to you to decide" ([10.1](https://git-scm.com/book/en/v2/Git-Internals-Plumbing-and-Porcelain)), and the core links forward into it, such as "See [Git Internals] for more information about exactly what files are contained in the `.git` directory" (`book/02-git-basics/sections/getting-a-repository.asc`) and "We'll go over the `refs/heads/` part in detail in [Git Internals]" (`book/03-git-branching/sections/remote-branches.asc`).

**Unteaching.** None explicit. Depth chapters flag their own approximations instead: Reset Demystified's three trees come with "There are a few cases where the index doesn't exactly act like a tree, but for our purposes it is easier to think about it this way for now", later "The index is not technically a tree structure -- it's actually implemented as a flattened manifest" (`book/07-git-tools/sections/reset.asc`, [7.7](https://git-scm.com/book/en/v2/Git-Tools-Reset-Demystified)), and Chapter 10 captions its first diagram "Simple version of the Git data model" ([10.2](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)). One near-miss: 1.3 says "Git doesn't think of or store its data this way" about deltas ([1.3](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F)), while 10.4 says that when Git packs objects it "stores just the deltas from one version of the file to the next" ([10.4 Packfiles](https://git-scm.com/book/en/v2/Git-Internals-Packfiles)). The model claim ("thinks of ... as snapshots") survives; the storage claim ("store") does not, and 10.4 never reconciles the two.

### MDN Learn web development

**Core.** Three tiers: Getting started ("for complete beginners"), Core ("essential skills and practices for being a successful front-end developer") and Extensions ("useful additional skills ... as you start to expand your knowledge and develop specialisms. Go onto these after you finish our Core") ([Learn web development](https://developer.mozilla.org/en-US/docs/Learn_web_development)). The Core modules are HTML, CSS styling basics, CSS text styling, CSS layout, JavaScript, JavaScript frameworks, accessibility, design for developers and version control ([Core](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core)).

**Evident criterion.** An end-to-end capability: Core covers "topics that we feel every web developer should have a good grounding in. This includes all the information they need to design and build a basic, accessible web app that follows modern best practices, and manage and deploy their code using appropriate tools" ([Core](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core)). The underlying [MDN Curriculum](https://developer.mozilla.org/en-US/curriculum/) grounds it in hiring: "Mozilla talks to industry professionals every day, and we regularly get feedback on the knowledge gaps in new hires", and sets depth per topic by how load-bearing it is: "Some are covered in depth, for example, HTML and CSS fundamentals. These are important to have a clear understanding of before a student goes too far on their learning journey. Some are covered more superficially, for example, version control or testing" ([About the curriculum](https://developer.mozilla.org/en-US/curriculum/about-curriculum/)). It also names exclusions, such as back-end languages and "Deep-dive DevOps topics" (same page).

**Return to depth.** Extensions are independent branches off the core: "While there is no specific prerequisite knowledge for starting any of these modules, it is advisable that you work through our Core modules first" ([Extensions](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions)). Each Extension names the core unit it extends; Advanced JavaScript objects requires "JavaScript object basics" and offers "a deeper knowledge of how JavaScript objects work ... JavaScript object theory and object-oriented programming practice" ([Advanced JavaScript objects](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Advanced_JavaScript_objects)). That is the map's Prereqs edge from a deep unit to its shallow counterpart.

**Unteaching.** None found in the pages read. The pages don't state an order among Extensions.

### Godot documentation

**Core.** Getting Started: an Introduction series, then "Step by step", then a first 2D game and a first 3D game. Step by step "builds upon the Introduction to Godot" and teaches nodes and scenes, instances, scripting, input and signals ([Step by step](https://docs.godotengine.org/en/stable/getting_started/step_by_step/index.html)). The 2D game is "intended for beginners who followed the complete Step by step" and has them build a whole small game ([Your first 2D game](https://docs.godotengine.org/en/stable/getting_started/first_2d_game/index.html)).

**Evident criterion.** Frequency of use: "Nodes, scenes, the scene tree, and signals are four core concepts in Godot that you will manipulate all the time" ([Overview of Godot's key concepts](https://docs.godotengine.org/en/stable/getting_started/introduction/key_concepts_overview.html)), then a complete small project as proof of the capability. Programming itself is explicitly outside the core: "Teaching programming foundations and how to think like a game developer is beyond the scope of Godot's documentation" ([Learning new features](https://docs.godotengine.org/en/stable/getting_started/introduction/learning_new_features.html)).

**Return to depth.** The manual is a topic reference, entered by need rather than read in order: "When learning a new topic, you can start by browsing the corresponding section of this website" (same page). Depth pages refer back to the core model and add layers beneath it; Using SceneTree opens "In previous tutorials, everything revolved around the concept of nodes. Scenes are collections of nodes. They become active once they enter the scene tree", then introduces MainLoop, SceneTree and the root viewport below what Getting Started showed ([Using SceneTree](https://docs.godotengine.org/en/stable/tutorials/scripting/scene_tree.html)).

**Unteaching.** None found. The depth page keeps "a game is a tree of nodes" and explains what sits under it.

### MIT Missing Semester

**Core.** A short course of lectures, each on one tool area; the 2026 edition runs shell, command-line environment, development environment, debugging and profiling, version control, packaging, agentic coding, "beyond the code" and code quality, with earlier years' special topics dropped ([Missing Semester](https://missing.csail.mit.edu/)).

**Evident criterion.** Everyday utility as judged by the instructors: the course "covers all the topics we consider crucial to be an effective computer scientist and programmer", motivated by students who "often perform repetitive tasks by hand" ([About](https://missing.csail.mit.edu/about/)). No formal selection method is stated.

**Return to depth.** Inside a lecture, model before commands. The Git lecture rejects a commands-first core: Git's interface is "a leaky abstraction", so learning it top-down leaves learners treating commands as "magic incantations"; "While an ugly interface has to be memorized, a beautiful design can be understood", so it gives "a bottom-up explanation of Git, starting with its data model" ([Version Control (2020)](https://missing.csail.mit.edu/2020/version-control/)). The 2026 lecture keeps that order: data model, staging area, command-line interface, then "Advanced Git" ([Version Control (2026)](https://missing.csail.mit.edu/2026/version-control/)).

**Unteaching.** None; the model comes first, so there's no shallow model to retract. The cost is that the core is not command-first, which is the opposite trade from Pro Git's "magic invocation".

### javascript.info

**Core.** Part 1 opens with "JavaScript Fundamentals" and "Objects: the basics", then deepens by topic: "Advanced working with functions", "Object properties configuration", "Prototypes, inheritance", "Classes" and so on ([javascript.info](https://javascript.info/)). The stated arc is "starting from scratch and go on to advanced concepts like OOP" (same page).

**Evident criterion.** Not stated beyond "from scratch". The structure shows a linear path in which each topic gets a basics chapter early and a depth chapter later, such as "Arrow functions, the basics" in Fundamentals and "Arrow functions revisited" in Advanced working with functions (same page).

**Return to depth.** Explicit revisits that add, not correct: "Let's revisit arrow functions. Arrow functions are not just a "shorthand" for writing small stuff. They have some very specific and useful features" ([Arrow functions revisited](https://javascript.info/arrow-functions)).

**Unteaching.** None found. Core chapters hedge claims so they stay true and point forward: keys "can be any strings or symbols (a special type for identifiers, to be covered later)", "Property keys must be strings or symbols (usually strings)", "We'll cover the special nature of `__proto__` in subsequent chapters", and "Here we've just scratched the surface of a topic that is really huge" ([Objects](https://javascript.info/object)).

### Bruner's spiral curriculum, and elaboration theory

The book's scans on the Internet Archive are lending-restricted, so these quotes come through a secondary source, Smith, "Jerome S. Bruner and the process of education", *the encyclopedia of informal education* (infed.org, 2002), read as the [PDF copy at METU OCW](https://ocw.metu.edu.tr/mod/resource/view.php?id=4240), with its page numbers to the 1960 Harvard edition. Check them against the book before quoting them anywhere load-bearing.

- **Core as structure.** "If earlier learning is to render later learning easier, it must do so by providing a general picture in terms of which the relations between things encountered earlier and later are made as clear as possible" (Bruner 1960: 12). This is the load-bearing test: the core holds the ideas later units relate to.
- **Honest early forms.** "We begin with the hypothesis that any subject can be taught effectively in some intellectually honest form to any child at any stage of development" (Bruner 1960: 33). This is the map's "true but incomplete" rule, as a hypothesis about what is possible.
- **Return to depth.** "A curriculum as it develops should revisit this basic ideas repeatedly, building upon them until the student has grasped the full formal apparatus that goes with them" (Bruner 1960: 13, as quoted). The spiral revisits the same ideas; it doesn't introduce corrected ones.

Reigeluth's elaboration theory makes the same move for sequencing: the first lesson is an epitome of the ideas that follow, and each later level elaborates it ([Reigeluth, Merrill, Wilson and Spiller 1980, *Instructional Science* 9](https://doi.org/10.1007/BF00177327); the article is paywalled and the [METU reprint](https://ocw.metu.edu.tr/mod/resource/view.php?id=4412) is an image scan, so this rests on its abstract). Its later Simplifying Conditions Method picks "the simplest version of the task to be taught" that is "still representative of the entire task", and each elaboration is "slightly more complex" ([EduTech Wiki](https://edutechwiki.unige.ch/en/Elaboration_theory), citing Reigeluth 1999 via Wiley 2000; secondary).

## How depth returns without contradiction

Patterns seen across the resources, each usable by fill agents:

- **Forward pointer at the cut.** The core unit names what it leaves out and where it lives: Pro Git's "For now this magic invocation is all you need ... We'll go into much more detail ... in [Reset Demystified]", javascript.info's "to be covered later". In a Curriculum this is the deep unit listing the core unit in Prereqs, plus a sentence in the core unit's body.
- **Hedged, true wording.** "usually strings" (javascript.info), "Git thinks about its data more like a stream of snapshots" (Pro Git 1.3). The hedge keeps the claim true when the exception arrives.
- **Procedure without mechanism.** Pro Git teaches `git reset HEAD <file>` as what to type, with no explanation, rather than a wrong explanation. Under the map's rule that Goals stay propositions, the core Goal is the observable fact ("`git reset HEAD <file>` unstages the file and leaves the working tree unchanged"), not a claim about how `reset` works.
- **Depth adds layers beneath.** Godot's Using SceneTree and Pro Git's Chapter 10 keep the core model and explain what implements it. Neither restates the core model differently.
- **Depth flags its own approximations.** When a depth unit itself simplifies, it says so in place ("for our purposes it's close enough", "Simple version of the Git data model"). The flag sits in the unit that simplifies, so a later unit refines it rather than retracting it.
- **State core claims at the model level, not the implementation level.** Pro Git's one near-miss is a core sentence about storage ("doesn't ... store its data this way"), which the internals chapter qualifies. The model-level sentence beside it ("thinks of its data ... as snapshots") stays true.

## Candidate criteria for the core cut

Each could be the criterion the outline agent states in Ordering rationale. They aren't exclusive; the last item combines them.

1. **Capability target.** The core is the least set of units that lets the learner do a stated end-to-end task, taken from the Brief, such as "clone a repository, see what has happened in the history of the project, modify files, and contribute changes" (Pro Git) or "build a basic, accessible web app ... and manage and deploy" it (MDN). Trade-offs: checkable at the checkpoint, and it names where a capstone project attaches; but the task statement sets the size, and a broad one bloats the core (MDN's Core includes frameworks).
2. **Frequency.** The core is what day-to-day practice uses most: "the 80% of cases" (Pro Git), "you will manipulate all the time" (Godot). Trade-offs: matches the map's "day-to-day work" wording and keeps the core small; but frequency is the agent's estimate, not measured data, and it drops rare but critical units such as recovering lost commits.
3. **Load-bearing model.** The core includes the thin slice of model without which the core procedures are "magic incantations" (Missing Semester) or the rest of learning goes badly (Pro Git 1.3, MDN's "important to have a clear understanding of before a student goes too far", Bruner's "general picture"). Trade-offs: it is what makes later units extend rather than contradict, because the deep units build on a model the core already stated truly; but it pulls theory forward, and without a bound it pulls the internals in too. Bound it: admit a model fact only if a core procedure's Goal depends on it.
4. **Simplest authentic whole task.** The core is the simplest version of the subject's real task that is still representative of the whole (elaboration theory's epitome and Simplifying Conditions). Trade-offs: fits procedural subjects like Godot, where the 2D game is that epitome; fits declarative subjects badly; and the sources for it are secondary.
5. **Closure (a check, not a selector).** No core unit has a branch unit in its Prereqs, and every branch can start from the core alone, as MDN's Extensions say: "no specific prerequisite knowledge ... it is advisable that you work through our Core modules first". Trade-offs: mechanically checkable, so it is a candidate `check` rule (see the map's "Not yet specified"); it doesn't choose what goes in, only rejects a cut that leaks.

**Suggested statement.** Take the capability target from the Brief (1); among the units that serve it, keep those day-to-day practice uses (2); admit a model unit only when a kept unit's Goal depends on it (3); then confirm the core is closed under Prereqs (5). Record each in Ordering rationale so the human can adjust at the checkpoint. This is how Pro Git's core is built: a capability list, held to the 80% case, with 1.3's model and 3.1's object model admitted because the commands and branching need them, and Chapter 10 left as a branch.

## Not found

- None of the resources states a written rule for the cut beyond the quotes above; the criteria are read off their stated aims and structure.
- No resource surveyed explicitly retracts a core claim; Pro Git's deltas wording is the only tension found, and it is implicit.
- Bruner's and Reigeluth's primary texts weren't readable online; their quotes here are from secondary sources, marked where used.
